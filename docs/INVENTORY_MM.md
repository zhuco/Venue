# Binance 库存做市

库存做市是独立策略类型 `inventory_mm`，不是对冲网格的参数组合。策略核心位于
`crates/venue-strategies/src/inventory_mm/`，控制与运行链位于
`apps/venue-control/src/inventory_mm/`。仅支持 Binance LIVE Hedge 线性永续，仍由现有
`venue-executor-binance` 单例、账户串行队列和 PostgreSQL 命令账本执行。

## 报价与库存

每个策略实例最多维持一笔买报价、一笔卖报价；这不是账户级交易对订单数量限制。
报价中心由盘口中间价与净库存偏移决定；
净多时中心下移，净空时上移。半边价差取基础半价差与波动估计乘系数的较大值。
波动估计复用现有 EMA 算法，输入为相邻中间价的绝对收益（bp），不是统计标准差。
重启后重新预热行情信号；它不是交易恢复日志。

初始配置的 `5bp` 是每侧最小半价差，不是完整买卖价差，也不是网格步距。
5U 是目标单笔名义额；开仓需按数量步长补足交易所最低名义额，补足后的实际金额仍须通过所有限额。
合法平仓不强制满足开仓最低名义额，但必须满足数量步长和最小数量，且不超过可平持仓。

所有风险量使用同一标记价格：净头寸为 `mark × (long − short)`，总头寸为
`mark × (long + short)`。单腿、总头寸、净头寸分别设限。400U 单腿库存容量不是400U下单目标；
20倍是发送前需验证的交易所设置，不是策略使用全部购买力的许可。

每次报价先按方向评估净风险，再选择平另一腿或开本腿。买入平空仍会增加净多，不能因为
是平仓而跳过净风险检查。正常循环不预先建立相等的两腿；多空可以共存，但对冲部分本身
不产生额外盈利优势。超过净限额时先撤销增险报价，再提出降低净头寸的平仓报价。

## 耐久边界与共存

- 保存只创建停止态，预检只读取事实；启动重新校验所有权、已验证托管凭证、Hedge、
  旧链互斥、账户未决命令及签名杠杆/保证金。首次启动要求目标交易对无仓位和挂单。
- 同账户可运行多个策略。“同账户同交易对只安排一个策略”由用户负责，不设置账户级策略数量
  限制、交易对占用唯一约束或 Grid/KOL/做市/手动操作之间的策略占用拦截。
  这不提供策略间仓位隔离：同交易对双腿仍是账户级事实，重叠操作会互相影响库存和盈亏。
  订单归属、账户串行、未决对账和各策略的签名持仓准入仍独立校验，不因用户自行排布而放宽。
- 报价、撤单使用独立 `inventory_mm` 命令来源及实例归属，不复用 Grid 的铺单、滚动锚点或热批次。
  适配器在报价的首次精确查单、重启查单及撤单查单中返回数量、累计成交量与终态事实；
  调度器不接受仅有订单号的 ACK。已确认的活动报价可完成命令入队操作，但不冒充订单成交或撤单终态。
- 更新报价必须先撤单，确认原身份的签名终态后重新规划；没有先挂新单后撤旧单的路径。
  已持久化但未出现在签名投影里的订单仍需等待；不能将暂时缺席当作成交。
- `ReconcileRequired` 保留原 `clientOrderId`，账户后续增险暂停。撤单只针对本实例已证明归属的订单。
- 私有投影短暂不健康或超过5秒有效期时，暂停新报价并撤销已证明归属的报价，按原循环等待恢复；
  连续30秒仍不可用才锁定为需要处理。恢复后重新预热波动信号，报价入队及发送仍须满足原5秒新鲜度、
  同代事实和账户队列检查。持仓模式变化、非预期条件单、风险限额及不确定命令仍直接锁定，
  已锁定实例不会因网络恢复自动重新启动。
  私流空闲连接每2秒发送心跳，收到响应才更新连续性时间；发送心跳或空轮询不刷新事实，
  原15秒无响应断流门保持不变，避免心跳周期与5秒做市准入门重合。
- 公共行情及签名风险读取的单次失败也只暂停报价并撤销自有订单；连续读取失败30秒才锁定。
  签名校准时钟只用于交易所请求签名，读取范围与收发事实统一使用本机时钟，避免正偏移误判有效响应。
  恢复时重新读取全部发送事实，行情采样断档仍按原规则预热；身份、计算、持仓模式与风险限额错误不进入重试。
- 串行发送后只有一侧仍在场时，若它与新鲜事实下完整风控后的目标报价精确一致，只补齐缺少的一侧。
  已有报价的价格、剩余数量或库存方向不再匹配时仍先撤再算；不延长旧命令有效期或放宽投影发送栅栏。
- 停止撤销本策略挂单，不自动平仓，也不改变 SOL 等其他交易对实例。保留仓位不等于无风险；
  后续启动仍要通过持仓准入，不隐式接管不明仓位。

## 保证金、损失和局限

实时新增名义额度来自新鲜签名可用保证金，扣除配置的账户保证金缓冲后，按确认杠杆与
明确的 USDC/USD 或 USDT/USD 换算证据计算。不能假设稳定币永远等于1美元。

损失上限、回撤上限和最小可用保证金以账户 **USD** 计量；损失基准和权益高点保存在数据库，
不会因进程重启清零。这是账户级保险开关，包含同账户 SOL、手续费、资金费等影响，
不能当作 XRP 策略独立收益。触发后停止增险并撤报价，状态持久化为需要处理；
仅撤挂单不保证库存损失止于配置金额，Maker 减仓也不保证立即成交。

本策略没有保本、固定收益或已验证盈利承诺。零 Maker 手续费不等于返佣，也不消除逆向选择。
界面、创建回执和命令入队不能证明实盘验收；需核对真实成交、手续费、原生终态和双腿持仓。
离线安全回归只验证实现契约，不是模拟交易运行模式，也不能替代实盘证据。

## 控制入口

协议位于 `crates/venue-control-protocol/src/inventory_mm.rs`：

- `GET /v2/strategies/inventory-mm`：本人实例列表。
- `POST /v2/strategies/inventory-mm`：新建独立停止态实例。
- `POST /v2/strategies/inventory-mm/preflight`：当前版本只读预检。
- `POST /v2/strategies/inventory-mm/lifecycle`：带请求身份和预期版本的启动/停止。

桌面机器人页使用独立“库存做市”入口与参数窗口，预检不自动启动。
受信运维入口为 `venue-strategy-admin mm-create USER`、`mm-preflight USER`、
`mm-lifecycle USER`（结构化请求从 stdin 输入）和 `mm-status USER INSTANCE`。
运维启动与用户 API 复用相同签名预检及锁内准入，不能通过改数据库状态跳过。
Hedge 原生订单的 `positionSide`、Post Only 和不发送禁止的 `reduceOnly` 参数由适配层处理，
参见 [Binance Portfolio Margin 交易接口](https://developers.binance.com/en/docs/catalog/advanced-trading-derivatives-trading-portfolio-margin/api/rest-api/trade)。

## 部署与验收门

迁移 `0045` 和新版本 Control/Executor 必须配套部署，不能只更新桌面端。
部署前确认现有 Grid 配置无已退役的非空 `inventory_risk` / `required_leverage` 字段、
账户无未决不确定命令、旧 writer 仍冻结。迁移由既有运维角色执行；新实例与生命周期表
还必须按现有最小权限规则授予 Control/Executor 运行角色访问权限，不能假设存在默认授权。

升级后先验证数据库迁移校验、运行二进制与发布清单哈希、单例服务状态及四个 HTTPS 路由，
再由账户使用者保存停止态实例、查看签名预检并明确启动。禁止用 SQL 修改实例状态代替启动。
实盘验收单独记录该实例的原生订单、成交、手续费与双腿持仓回读；编译、离线回归及 HTTP
成功均不代表通过实盘验收，也不能证明策略盈利。
